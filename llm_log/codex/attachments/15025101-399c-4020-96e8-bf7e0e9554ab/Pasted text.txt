\[

5. Part 1 — Serial heat diffusion solver
Mathematical problem
We solve the two-dimensional heat equation:
\[
\frac{\partial u}{\partial t}
=\alpha\left(
\frac{\partial^2u}{\partial x^2}
+\frac{\partial^2u}{\partial y^2}
\right)
\]

The domain is the unit square.

The grid contains:
\[
(N+1)^2
\]

total points and:
\[
(N-1)^2
\]

interior points.

The spatial step is:
\[
h=\frac{1}{N}
\]

With thermal diffusivity \(\alpha=1\):
\[
\Delta t=rh^2
\]

The explicit five-point stencil is:
\[
u_{i,j}^{n+1}=(1-4r)u_{i,j}^{n}
+r\left(
u_{i-1,j}^{n}
+u_{i+1,j}^{n}
+u_{i,j-1}^{n}
+u_{i,j+1}^{n}
\right)
\]

The stability condition is:
\[
\boxed{r\leq0.25}
\]

Implemented simulation cases
Case 1
Four hot boundaries

Case 2
Hot top and bottom, cold sides

Case V
Sinusoidal initial condition, cold boundaries


Case 1 and Case 2 start with zero interior temperature. Case 2 uses hot corner values, consistent with the top and bottom boundary conditions.

Case V has the initial condition:
\[
u(x,y,0)=\sin(\pi x)\sin(\pi y)
\]

Its analytical solution is:
\[
u(x,y,t)=
\sin(\pi x)\sin(\pi y)e^{-2\pi^2t}
\]

Implementation details
- Contiguous row-major double arrays.
- Two buffers: current and next temperature.
- Update interior points only.
- Fixed physical boundary values.
- Swap buffers after each time step.
- Command-line parameters.
- Optional binary output.
- Maximum error and discrete L2 error.
- Timing with separate computation and communication fields.
Example:
~/part1/heat --decomp serial --case V \
    --N 64 --r 0.2 --T 0.05


Convergence verification
With Case V, r=0.2 and T=0.05:

The observed convergence order was approximately two, confirming second-order convergence under the chosen time-step refinement.

We also demonstrated instability using r=0.2625. Numerical errors grew dramatically, producing a checkerboard instability pattern.

7. Part 3 — MPI 2D block decomposition
Objective
Divide the interior grid into rectangular blocks using a two-dimensional Cartesian MPI topology.
Blocks exchange horizontal and vertical halo data.
Implemented MPI functions
Function	Purpose
MPI_Dims_create	Select process grid dimensions
MPI_Cart_create	Create Cartesian topology
MPI_Cart_coords	Find rank coordinates
MPI_Cart_shift	Identify neighbors
MPI_Type_vector	Describe non-contiguous columns
MPI_Type_commit	Activate derived datatype
MPI_Sendrecv	Exchange halo values
MPI_Reduce	Collect timing and error statistics
MPI_Gatherv	Gather variable-sized blocks
MPI_Type_free	Release datatype resources
MPI_Comm_free	Release Cartesian communicator

Process grid dimensions
P	Py × Px
1	1×1
2	2×1
3	3×1
4	2×2
5	5×1
6	3×2
8	4×2

Balanced decomposition
For each dimension, the local number of points is calculated using:
base = total / parts;
rem = total % parts;

count = base + (coord < rem);
start = 1 + coord * base + min(coord, rem);


Each local block contains:
(nx + 2) × (ny + 2)


elements, including its ghost layer.

The memory index is:
idx(y, x) = y * width + x;


Halo exchange
Four communication operations are used:
Exchange	MPI tag
Send top row, receive bottom ghost	100
Send bottom row, receive top ghost	101
Send right column, receive left ghost	102
Send left column, receive right ghost	103

Rows are contiguous in memory.

Columns are described using:
MPI_Type_vector(ny, 1, width,
                MPI_DOUBLE, &column_type);


Corner ghost values are not exchanged because the five-point stencil does not require diagonal neighbors. A nine-point stencil would require diagonal information.

Theoretical analysis
For a typical interior strips process:
\[
T_{\text{comm,strips}}
\approx2t_s+2Nt_w
\]

For an interior process in a square block decomposition:
\[
T_{\text{comm,blocks}}
\approx4t_s+
\frac{4N}{\sqrt P}t_w
\]

Blocks reduce halo data sizes but may require more messages. Therefore, latency, bandwidth, process placement and grid size determine which decomposition is faster.

Theoretical predictions were prepared for:
- N=512, 2048 and 8192.
- P=4 and P=8.
The model was also refined to account for actual rectangular process grids and physical boundaries.

13. Part 4 — Theoretical performance model
We combined Part 0 network measurements with Part 4 computation rates.

The general model is:
\[
T_{\text{step}}=
T_{\text{comp}}+T_{\text{comm}}
\]

For homogeneous processors:
\[
T_{\text{comp}}\approx
\frac{(N-1)^2}{P}t_c
\]

The refined model accounts for:
- Different computation speeds for each VM.
- Actual domain decomposition.
- Physical boundaries.
- Neighboring ranks.
- Process placement.
- Same-VM and cross-VM network costs.
Predictions versus measurements
N=512, slot placement, milliseconds per time step:
P	Strips predicted	Strips measured	Blocks predicted	Blocks measured
1	0.550	0.615	0.550	0.563
2	0.285	0.453	0.285	0.577
3	6.055	16.608	6.046	26.334
4	6.009	291.090	4.831	111.768
5	7.021	77.592	7.010	61.547
6	7.008	Incomplete	10.297	Incomplete

The model predicts the general degradation when moving from local to distributed MPI execution, but it considerably underestimates actual communication delays.

Potential causes include unstable Wi-Fi, Tailscale relays, MPI synchronization, network contention, heterogeneous processors and memory effects.

The model is an approximation, not an exact simulation of MPI runtime behavior.

Question 1 — When does distributing across machines become beneficial?
No completed distributed measurements demonstrate a speed improvement over local execution at N=512 or N=2048.

Our theoretical model predicts that distributed execution may become beneficial at N=8192.

This predicted crossover could not be verified experimentally because the distributed N=8192 experiments repeatedly failed.
Question 2 — Why do theoretical and measured performance differ?
The theoretical model assumes relatively stable computation and communication costs.

The actual environment has variable network latency, heterogeneous processors, MPI waiting time, virtualization overhead and possible memory effects.

Repeated Tailscale and TCP connectivity failures contributed to difficulties collecting reliable measurements.
Question 3 — What would change with a real cluster having 1 µs latency?
Reducing startup latency significantly improves theoretical performance, particularly for smaller grids.

For larger grids, computation and bandwidth become more important.

A latency-only hypothetical model was calculated while holding our measured bandwidth and computation costs constant.

These results are theoretical predictions, not real high-performance cluster measurements.
Question 4 — What recommendations would we give for using Tailscale?
Use direct connections where possible, stable physical networks, appropriate process placement, similar machine capabilities and repeated benchmark measurements.

Prefer local MPI execution for small workloads.

Consider 2D blocks for sufficiently large problems, but measure their performance instead of assuming they will always be faster.

Avoid oversubscription.
